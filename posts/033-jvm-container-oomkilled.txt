This lived in a Spring Boot payment service on Kubernetes with a 768Mi memory limit. Under load the pods kept getting recycled, yet the logs were clean — no OutOfMemoryError, no stack trace, nothing pointing at our code. We went hunting for a heap dump and there wasn't one, because the JVM never threw anything. The Linux kernel had killed the process from underneath it, and 𝗲𝘅𝗶𝘁 𝟭𝟯𝟳 is just 128 + 9 — a 𝗦𝗜𝗚𝗞𝗜𝗟𝗟 from the cgroup OOM killer, not a JVM failure.

The mechanism was almost embarrassing. The JVM was sizing its max heap from the node's total memory, not the container's limit. On an older runtime the default max heap is about a quarter of the RAM the process thinks it can see, and a container without cgroup awareness sees the whole host. So on a 64GB node the JVM assumed it could grow the heap into gigabytes, while the real limit sat at 768Mi. The heap expanded as designed, resident memory crossed the limit, and the kernel killed the container instantly — no Java exception, because from the JVM's point of view it was still inside 𝗶𝘁𝘀 heap.

Even with container awareness on, the heap is only one slice of what the kernel counts. Metaspace, thread stacks, the JIT code cache, direct ByteBuffers and Netty's off-heap pools all live outside -𝗫𝗺𝘅 — set the heap to 75% and forget the rest, and you get killed again.

• leave real headroom for off-heap — metaspace, thread stacks, direct buffers, GC — 75% heap is aggressive for heavy IO and Netty work

• watch the container's 𝗥𝗦𝗦 and working set, not only heap-used — a healthy heap graph next to a climbing RSS is exactly the trap

A JVM tuned as though it owns the whole machine, dropped into a container that owns a slice of it, loses that argument every time — quietly, handing you a number where you expected a stack trace.
