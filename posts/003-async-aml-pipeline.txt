We had exactly that setup at some point. A request comes in → call AML → wait → continue. It worked fine… until load increased and reality kicked in: slow providers, retries piling up, threads getting blocked, response times going up. Typical situation when external integrations sit directly in the request path, especially when retry logic starts amplifying the problem instead of helping.

So we moved AML processing out of the request flow and turned it into an 𝗮𝘀𝘆𝗻𝗰, 𝘀𝘁𝗮𝘁𝗲-𝗱𝗿𝗶𝘃𝗲𝗻 𝗽𝗶𝗽𝗲𝗹𝗶𝗻𝗲. Instead of waiting on AML, we persist the operation and let background jobs handle it. A scheduler (cluster-safe with locking) picks up operations in batches and processes them in parallel using a bounded thread pool, while external calls are wrapped with 𝗿𝗲𝘁𝗿𝘆 + 𝗯𝗮𝗰𝗸𝗼𝗳𝗳 so transient failures are handled without overloading the system or blocking user requests.

The key here wasn’t just “make it async”, but actually 𝗰𝗼𝗻𝘁𝗿𝗼𝗹 𝘁𝗵𝗲 𝗳𝗹𝗼𝘄 𝗲𝗻𝗱-𝘁𝗼-𝗲𝗻𝗱 — predictable retries, clear state transitions, bounded concurrency, and no hidden thread explosions 🙂 In production this setup handles 𝘁𝗲𝗻𝘀 𝗼𝗳 𝘁𝗵𝗼𝘂𝘀𝗮𝗻𝗱𝘀 𝗼𝗳 𝗼𝗽𝗲𝗿𝗮𝘁𝗶𝗼𝗻𝘀 𝗽𝗲𝗿 𝗱𝗮𝘆 under high load without impacting latency or stability.

Big takeaway for me: if your core flow depends on slow external services, pushing it into an async pipeline with proper retry/backoff and state management is not an optimization — it’s a necessity 😅 Curious how others approach this — async from the start, or only after things start breaking under load? 🤔
